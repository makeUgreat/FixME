# 문서 작성 컨벤션

문서 작성 규칙은 agent와 contributor가 같은 구조, 문체, 유지보수 기준으로
프로젝트 문서를 작성하도록 돕는다. README, AGENTS instruction, project guide,
cross-project convention을 만들거나 수정할 때 이 컨벤션을 따른다.

API 전용 구현 규칙은 `apps/api/docs/{en,kr}`에 둔다. 레포 전체 문서 규칙은
`docs/{en,kr}`에 둔다.

## 원칙

- 문서를 읽고 결정을 내려야 하는 다음 contributor를 기준으로 쓴다.
- 부수적인 구현 세부사항보다 의도, 규칙, 예외, 검증 방법을 먼저 설명한다.
- 문서는 자신이 다루는 범위와 가까운 위치에 둔다.
- 일시적인 맥락보다 안정적인 project fact를 우선한다.
- 번역 쌍으로 관리되는 문서를 수정하면 대응하는 영어 또는 한국어 문서도 함께
  갱신한다.

## 구조

- 제목은 문서의 실제 역할을 드러내는 이름으로 쓴다.
- 첫 단락은 문서가 해결하는 문제, 적용 범위, 독자를 짧게 설명한다.
- 컨벤션 문서는 기본적으로 `Principles`, `Rules`, `Examples`, `Testing` 또는
  `Verification` 흐름을 사용한다.
- 단순 가이드는 기본적으로 `Purpose`, `Usage`, `Commands`, `Notes` 흐름을
  사용한다.
- 섹션은 한 가지 주제에 집중한다. 서로 다른 결정을 섞고 있으면 섹션을 나눈다.
- 규칙 전체를 반복하기보다 그 규칙을 소유하는 가장 구체적인 문서로 링크한다.

## 문체

- 짧고 직접적인 문장을 사용한다.
- 규칙의 강도가 중요하면 `must`, `must not`, `should`의 의미가 드러나게 쓴다.
- "적절히", "일반적으로", "필요하면", "잘" 같은 모호한 표현은 판단 기준을
  함께 제시할 수 있을 때만 사용한다.
- 누가 또는 무엇이 동작을 수행하는지 드러나는 능동 표현을 우선한다.
- 코드 이름, 파일명, 명령어, type 이름, layer 이름은 정확히 유지한다.
- 미래 시스템을 이미 존재하는 것처럼 쓰지 않는다.

## 한영 문서 쌍

- 영어 문서와 한국어 문서는 같은 의미를 유지한다.
- 자연스러운 기술 한국어가 더 명확하다면 직역을 강제하지 않는다.
- 코드, 파일 경로, 명령어, package 이름, class 이름, type 이름, 코드에서 이미
  쓰는 domain term은 번역하지 않는다.
- 한쪽 언어만 수정했다면 작업을 마치기 전에 대응 문서도 갱신한다.
- 의도적으로 한 언어로만 제공하는 문서라면 문서 상단에 그 사실을 적는다.

## 예시

규칙이 추상적이거나 오해하기 쉬우면 예시를 사용한다.

좋은 예시:

- 현재 repository structure와 naming convention에 맞는다.
- 가장 작지만 유용한 case를 보여준다.
- 필요할 때 API 또는 workspace의 실제적인 이름을 사용한다.

나쁜 예시:

- 존재하지 않는 큰 imaginary module을 도입한다.
- 규칙을 관련 없는 business logic 뒤에 숨긴다.
- naming convention과 충돌하는 이름을 사용한다.

## 유지보수

- 새 컨벤션이 agent behavior를 안내해야 한다면 `AGENTS.md`에 링크를 추가한다.
- 사람이 문서를 찾는 데 도움이 될 때만 README pointer를 추가한다.
- 레포 전체 컨벤션은 `docs/{en,kr}` 아래에 둔다.
- API 전용 컨벤션은 `apps/api/docs/{en,kr}` 아래에 둔다.
- 문서를 이동하거나 이름을 바꾸면 relative link를 확인한다.

## 검증

문서 변경을 마치기 전에 다음을 확인한다.

- 링크가 링크를 포함한 파일 기준으로 올바르게 resolve된다.
- 영어와 한국어 문서가 같은 규칙을 설명한다.
- 문서가 자신의 적용 범위를 명확히 말한다.
- 예시가 현재 project structure와 맞는다.
- agent-facing convention은 `AGENTS.md`에서 참조한다.
